This page shows how a bean runs its own code right after Coilix creates it and again when the application stops. Use it when a bean has to check its settings, open a resource or start a thread pool, and release it later.

## Mark the lifecycle methods

Annotate a method with `@PostConstruct` to run it once after the bean is created and its dependencies are injected. Annotate a method with `@PreDestroy` to run it when the application context closes.

<CodeBlock language="scala" title="ReportScheduler.scala">{ReportScheduler}</CodeBlock>

A lifecycle method takes no parameters and returns `Unit`. It can be private, as in the example, and it can be declared in a superclass of the bean. If a bean has several methods with the same annotation, Coilix runs them in order of their names. For a bean made by a `@Bean` method, Coilix looks at the class of the returned object, so a method declared as `def gateway: Gateway = HttpGateway()` still runs the lifecycle methods of `HttpGateway`.

A method with parameters or with a result other than `Unit` stops the startup with `InvalidLifecycleMethodException`. The message names the bean and the method. A lifecycle method may also return `IO[Unit]`, as described in [cats-effect](cats-effect.mdx#lifecycle-methods-in-io).

## When the methods run

Coilix runs the `@PostConstruct` methods before it passes the bean to any other bean. A bean that receives `ReportScheduler` in its constructor always gets a scheduler that has already checked its settings.

If a `@PostConstruct` method throws an exception, the startup stops with `BeanCreationException`. The message names the bean and the method, and the original exception is its cause.

The application context closes when the application ends, for example after `SIGTERM` or Ctrl+C. Coilix then runs the `@PreDestroy` methods, starting with the bean that was created last. A bean is therefore destroyed before the beans it depends on, so it can still use them while it stops.

If a `@PreDestroy` method throws an exception, Coilix logs it as a warning and goes on with the remaining methods and beans.

## Order beans without injecting them

Coilix creates a bean after the beans it receives in its constructor. Sometimes a bean relies on another one only through a side effect: a price cache reads a table that the schema migrations create, but it never calls the migrations. Name such beans in `@DependsOn` on the class or on a `@Bean` method:

<CodeBlock language="scala" title="lifecycle/PriceCache.scala">{PriceCache}</CodeBlock>

Coilix creates `schemaMigrations` and runs its `@PostConstruct` methods before it creates `PriceCache`, and destroys `PriceCache` first when the context closes. A lazy bean named in `@DependsOn` is created just before the bean that names it.

A name that matches no bean stops the startup with `NoSuchBeanException`, and a name of a `@Prototype` bean with `BeanCreationException`, because a prototype has no single instance to create first. Beans that depend on each other through `@DependsOn` stop the startup with `CircularDependencyException`, as with constructor parameters. A bean that a test replaces with `replaceBean` is ready before any bean is created, so a name of a replaced bean waits for nothing.

## React to the whole context

A bean that needs every other bean, or that must stop its work before any bean is destroyed, implements `ContextLifecycleListener`. Coilix calls `onContextStarted` once all beans exist, and `onContextClosing` when the context closes, before the first `@PreDestroy` method.

The closing goes through four phases, whatever the order in which the beans were created:

1. `ClosingPhase.Announcement` tells the application that it is closing, before anything stops. The events module publishes `ContextClosing` here.
2. `ClosingPhase.Producers` stops whatever brings new work in, such as `@Scheduled` methods, message consumers and servers. A listener is in this phase unless it says otherwise.
3. `ClosingPhase.Events` finishes the work that was already accepted, such as queued messages.
4. `ClosingPhase.Resources` releases what the work needed, such as connections.

Only then do the `@PreDestroy` methods run. Within one phase, the listener created last is called first. The outbox below sends its queued orders in the `Events` phase. By then no scheduled task adds new orders, and the mail sender is still available:

<CodeBlock language="scala" title="lifecycle/OrderOutbox.scala">{OrderOutbox}</CodeBlock>

If `onContextStarted` throws an exception, Coilix closes the context and the startup stops. If `onContextClosing` throws, Coilix logs it as a warning and goes on with the closing.
