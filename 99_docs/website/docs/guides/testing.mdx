This page shows how to test your beans together, in the same application context that Coilix builds at startup. Use it when a test should check how beans work with each other, with the configuration and with profiles, while some beans are replaced by test doubles.

## Add the testkit

Add `coilix-testkit` to the test dependencies, next to munit:

```scala
libraryDependencies += "dev.coilix" %% "coilix-testkit" % "<version>" % Test
libraryDependencies += "org.scalameta" %% "munit" % "<version>" % Test
```

The testkit does not bring its own munit version, so your build decides which one is used.

## Write a test

Mix `CoilixSuite` into a munit suite and describe the context with `CoilixTestSetup`. Each `coilixTest` builds a fresh context, runs the test body inside it and closes it afterwards, which also runs the `@PreDestroy` methods.

<CodeBlock language="scala" title="RecordingMailer.scala">{RecordingMailer}</CodeBlock>

The setup declared as a `given` is used by every `coilixTest` that names no setup. A test that needs something else passes its own, usually built from the given one, as the second test above does.

`forApplication` scans the same packages as the application itself. To scan other packages, start from `CoilixTestSetup.forPackages("com.example.billing")`.

A test context differs from a running application in a few ways: it prints no banner and no startup log and does not call the `ApplicationRunner` beans. Call `withRunners` when a test needs them.

## Read from the context

Inside a test body the context is given, so the helpers need no reference to it:

| Helper | Returns |
|---|---|
| `bean[T]` | the bean of type `T`, or the primary one when there are several |
| `beanOption[T]` | the bean of type `T`, or `None` |
| `beans[T]` | every bean of type `T` |
| `property[T]("path")` | the configuration value converted to `T`, or `None` |
| `arguments` | the command-line arguments |
| `context` | the application context itself |

Your own helpers can take the context the same way, for example `def mailer(using ApplicationContext): Mailer = bean[Mailer]`. Outside `CoilixSuite`, mix in `CoilixContextOps` or import `CoilixContextOps.*`.

## Set properties and profiles

A test context only logs fatal errors (`coilix.fatal-errors.action = log`), so a test does not end the JVM. [Fatal errors](fatal-errors.mdx) shows how to test the shutdown.

`withProperties` sets configuration keys for the test. They win over every other source: command-line options, system properties and configuration files, including `application.yaml` in your test resources.

`withProfiles("dev", "local")` makes these profiles active for the test, in this order. It replaces `coilix.profiles.active` from every other source, so the test does not depend on how the build or the machine is set up.

`withArguments("--region=eu")` passes command-line arguments. They are available as `arguments`, and options also become configuration keys, as at startup.

## Replace and add beans

`replaceBean[Mailer](mailer)` removes every bean that can be injected as a `Mailer`, whether it comes from scanning, from a `@Bean` method or from a module, and puts the given instance in its place. Beans that need a `Mailer` get the test double. If the application has no bean of that type, building the context fails, so a wrong type does not go unnoticed.

`addBean[Uplink](uplink)` adds an instance next to the beans of the application. Use it for a bean the application does not define, for example to fill an `Option[Uplink]` dependency that is empty in production.

Coilix does not create test doubles for you. Pass a small class written for the test, as in the example, or an object from the mocking library you prefer.
