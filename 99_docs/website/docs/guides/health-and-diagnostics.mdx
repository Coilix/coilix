This page explains how an application built with Coilix reports its health and how it watches its own threads. Both come with `coilix-boot`, so every application has them without extra setup.

## Liveness and readiness

The `Health` bean answers two questions:

- **liveness**: is the application alive? An application that is not alive does not recover by itself and should be restarted, for example after a deadlock.
- **readiness**: should the application get new work? An application that is not ready works, but needs a break, for example while a backlog is cleared.

Each answer is `Up`, `Degraded` or `Down`. The answers come from `HealthIndicator` beans. An indicator has a name, a kind (`Liveness` or `Readiness`) and a current state with a reason. Liveness is the worst state of the liveness indicators, and readiness is the worst state of all indicators, because an application that is not alive is not ready either.

The built-in `startup` readiness indicator is `Down` while the application starts and turns `Up` when its runners have finished, so a load balancer sends no traffic to an application that is still warming up. After a failed start it is `Down` with the failure as the reason.

The diagnostics thread reads every indicator every `coilix.diagnostics.interval` (5 seconds by default), so `state` must be quick and must not block. Health endpoints over HTTP will come with the web module. Until then, read `Health` from your own code, for example `health.readiness == HealthStatus.Up`, and call `health.refresh()` when you need the newest state at once.

## Thread checks

The diagnostics thread, `coilix-diagnostics`, is a platform thread of its own, outside the pools of the application, so it keeps working when they are stuck. Each round it takes a snapshot of the platform threads and runs the `ThreadCheck` beans:

| Check | Finding | When |
|---|---|---|
| `DeadlockCheck` | `Critical` | Threads wait for each other forever, on monitors or on locks of `java.util.concurrent`. |
| `ThreadCountCheck` | `Warning`, `Critical` | More than `warning-count` or `critical-count` platform threads are alive. |
| `LongBlockedCheck` | `Warning` | A thread has been blocked on a monitor for at least `blocked-after`. |
| `ThreadGrowthCheck` | `Warning` | The thread count grew by `growth-limit` within `growth-window`, which suggests that threads leak. |

The `findingReporter` bean logs the findings with the stacks of the threads involved. A `Critical` finding is logged every round, while a warning of one kind is logged again only after `repeat-after`, so a lasting problem does not flood the log. To send findings somewhere else, register your own `FindingReporter` bean. To add a check, register a bean that implements `ThreadCheck`.

## Deadlocks

Deadlocked threads never recover, so by default (`on-deadlock: shutdown`) Coilix hands a `ThreadDeadlockException` to the `FatalErrorHandler`. It closes the context and ends the process, as described in [Fatal errors](fatal-errors.mdx), and the orchestrator starts a new instance. The halt after `coilix.fatal-errors.shutdown-timeout` matters here, because closing may wait for the deadlocked threads.

With `on-deadlock: report` Coilix only logs the deadlock and sets the `threads` liveness indicator to `Down`. Use it when an orchestrator restarts the application after a failed liveness check.

## Virtual threads

The JVM management API does not report virtual threads, so these checks see only platform threads. A deadlock between tasks on virtual threads, for example on the `BlockingExecutor`, is not found yet. To look at the threads of a running application yourself, write a thread dump with every virtual thread and the locks it waits for and holds (JDK 25 and newer show the locks):

```bash
jcmd <pid> Thread.dump_to_file -format=json threads.json
```
