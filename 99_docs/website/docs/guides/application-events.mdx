This page shows how one bean tells others that something happened without depending on them. The checkout publishes that an order was placed, and the statistics, the loyalty program and the mailer react to it. The checkout does not know any of them, so adding another reaction does not change it.

Events live only in the memory of the running application. An event that is still waiting for an asynchronous listener is lost when the process crashes, it is not delivered again after a restart, and it does not reach other replicas. When work must happen for sure, even after a failure, use durable processing instead of events.

A bean can also extend `ApplicationEventListener` with the event type. The type argument must be written in the class, so a lambda does not work here:

<CodeBlock language="scala" title="LoyaltyProgram.scala">{LoyaltyProgram}</CodeBlock>

A listener receives events of its type and of every subtype, so a listener of a sealed trait receives each of its cases. Type arguments count too: a listener of `Changed[Customer]` does not receive `Changed[Product]`.

Coilix finds the listeners when every bean of the application exists. An event published earlier, for example in a `@PostConstruct` method that returns `IO[Unit]`, waits and is delivered right after the start. A listener method that takes more or fewer than one parameter, returns something other than `IO`, or has the same name as another listener method of its bean stops the startup with `InvalidEventListenerException`.

## Synchronous and asynchronous listeners

By default the effect of a listener runs in the fiber of the publisher, before the effect of `publish` ends. When the checkout goes on, the statistics and the points are already updated. If a listener fails, the other synchronous listeners still run, and `publish` then fails with the first error with the others attached as suppressed.

Set `async = true` when the publisher should not wait, for example for a mail:

<CodeBlock language="scala" title="ConfirmationMailer.scala">{ConfirmationMailer}</CodeBlock>

An asynchronous listener runs on a fiber of its own, which starts with the MDC of the publisher when the application uses `coilix-logging` (see [Logging](logging.mdx)). A listener that waits, like the mailer above for the mail server, wraps the call in `IO.blocking`, so it does not hold a compute thread while it waits. A bean that implements `ApplicationEventListener` overrides `async` instead. Asynchronous listeners start only after every synchronous listener has succeeded. Their errors do not reach the publisher; Coilix logs them. Asynchronous deliveries run in no particular order, even for one listener. When order matters, use a synchronous listener.

## Retry an asynchronous listener

An asynchronous listener is tried once by default. Give it a retry policy under `coilix.events.listeners.<bean>.<method>.retry`, with the keys of `RetryPolicy` described in [Retry failed work](tasks-and-scheduling.mdx#retry-failed-work). Keys that are not set keep their defaults:

<CodeBlock language="yaml" title="application.yaml">{EventsYaml}</CodeBlock>

A listener that implements `ApplicationEventListener` uses `onEvent` as its method name. After the last try the event is logged and dropped for that listener. Synchronous listeners do not retry; Coilix warns at startup when one of them has a retry policy.

## What happens when the application stops

Coilix first publishes `ContextClosing`, described below. Then `@Scheduled` methods and other sources of new work stop. After that, in the `Events` phase of closing described in [Bean lifecycle](bean-lifecycle.mdx#react-to-the-whole-context), the event bus:

1. refuses events published from outside listeners, so no code counts on a delivery that would not happen: `publish` throws `EventBusClosedException`, and `tryPublish` returns `PublishError.Closing` or `PublishError.Closed`, so code that may run during closing decides itself what to do, for example log the event it could not publish,
2. ends the retries that are still waiting,
3. waits for the running asynchronous listeners, including the ones that receive events published by other listeners in the meantime,
4. after `coilix.events.shutdown-timeout` (10 seconds by default) cancels the listeners that still run and logs how many deliveries of each listener were abandoned.

Only then are the beans destroyed, so a listener never uses a closed bean. In Kubernetes, keep `terminationGracePeriodSeconds` longer than the shutdown timeouts of the events and of the executor together.

## Events of the framework

Coilix publishes its own events, which any listener can receive like the events of the application:

| Event | When |
|---|---|
| `ContextReady` | every bean exists and every `ContextLifecycleListener` has started, before the first `ApplicationRunner` |
| `ApplicationStarted` | every `ApplicationRunner` has finished |
| `ContextClosing` | the application starts closing, before `@Scheduled` methods stop and before any bean is destroyed |
| `ApplicationFailed` | a runner or a listener of `ContextReady` or `ApplicationStarted` has thrown an exception; the event carries it, and the application closes right after |

The shop below opens when the application has started and closes as soon as it starts stopping:

<CodeBlock language="scala" title="ShopStatus.scala">{ShopStatus}</CodeBlock>

An error of a listener of `ContextReady` or `ApplicationStarted` stops the startup like an error of a runner. An error of a listener of `ContextClosing` or `ApplicationFailed` is only logged, so the closing goes on. The application waits for asynchronous listeners of `ContextClosing` like for every other asynchronous delivery. A failure while the beans are created is not published as `ApplicationFailed`, because no listener exists yet.

## Test code that uses events

The event bus works in tests as in the application, and a test context publishes the events of the framework too. The testkit adds three helpers:

- `recordedEvents[E]` returns the events of type `E` published in the test so far, including the events of the framework,
- `awaitEvents()` waits until no asynchronous listener runs, by default for at most 5 seconds, and returns `false` when the time runs out; a test in `IO` calls `awaitIdle` of the `EventBus` bean instead,
- `withSynchronousEvents` on the setup runs asynchronous listeners in the fiber of the publisher, so their effects are visible right after `publish`. Their exceptions are still only logged, and retries follow at once, without waiting.
