This page shows how to run long background work, such as an export or a loop that watches for new orders, as a background processor. Coilix splits the work of a processor into shards, runs each shard of this replica on its own virtual thread, restarts it after a failure and stops it when the application closes.

## Add the module

Add `coilix-processing` to the dependencies:

```scala
libraryDependencies += "dev.coilix" %% "coilix-processing" % "<version>"
```

The module adds the `processorManager` bean, the only way to reach the processors.

## Name the processors

Each processor has an identifier, usually a `case object` of a sealed trait of the application. The manager takes identifiers, not names, so a misspelt processor does not compile:

<CodeBlock language="scala" title="ShopProcessor.scala">{ShopProcessor}</CodeBlock>

The name of an identifier is the name of the object in kebab case, such as `invoice-export`. It is used in the configuration, in thread names and in logs. Override `name` to keep an older name.

## Write a processor

A processor is a class with `@Processor` that extends a style of processor. Its constructor receives beans and `@Value` parameters like a bean, and its `@PostConstruct` and `@PreDestroy` methods run, but it is not a bean: no bean can inject it.

A `BlockingProcessor` does the work of one shard in `run`. This export splits the customers between its two shards by the slot of each customer and ends when its customers are sent:

<CodeBlock language="scala" title="InvoiceExport.scala">{InvoiceExport}</CodeBlock>

Work that never ends by itself checks `shard.stopRequested` and returns when the shard stops:

<CodeBlock language="scala" title="OrderWatch.scala">{OrderWatch}</CodeBlock>

A shard that does not stop within half of the stop timeout gets its thread interrupted. A `CustomProcessor` starts work that runs on its own threads and returns an `Execution`, which the manager stops and waits for.

`prepare` runs before every start of a shard, for example to restore its offsets. `onAcquired` and `onReleased` tell when this replica takes over and gives up a shard, with the reason: `Shutdown`, `Stopped`, `Completed` or `Failed`.

## Process elements from a source

A `StatelessProcessor[T]` handles elements that come from a source, one at a time and without state between them. The worker of each shard reads the source of the shard, calls `process` for each element in order and acknowledges the element when `process` returns:

<CodeBlock language="scala" title="InvoiceMailer.scala">{InvoiceMailer}</CodeBlock>

The source is an `InputSource[T]`, created for each start of a shard. It reads only the slots of that shard and gives each element as an `Input` with its slot, a stable `InputId` and the delivery number. The worker calls `poll` in a loop on its own thread, so a connector may simply block in it. When the shard stops or restarts, the worker closes the source, and the source delivers again every element that was not acknowledged.

When `process` throws, the worker fails with an `ElementFailedException` that names the element, and it restarts after the backoff of the restart policy. The element comes again with a higher delivery number, which `ElementContext.delivery` shows. Handling of failures per element, such as retrying or skipping, comes later.

`InMemoryStream` is a source in memory with slots, for tests, demos and work that may be lost when the process ends. `publish` puts each element into the slot of its key, so the elements of one key keep their order. `InMemoryOutput` keeps what a processor emits:

<CodeBlock language="scala" title="OrderStream.scala">{OrderStream}</CodeBlock>

A source that defines its own number of slots, like the partitions of a topic, needs the same `slots` for the processor; otherwise its shards fail at start with the key to set.

## Slots, shards and replicas

The data of a processor is split into slots, 256 by default. A slot is fixed: `ShardKeys.slotOf` gives the same slot for a key whatever the number of shards or replicas. Slot `s` belongs to shard `s % shards`, and each shard runs on one replica:

- `round-robin`, the default, runs shard `i` on replica `i % replicas`,
- `range` runs a contiguous range of shards on each replica,
- `pinned` runs every shard on `pinned-replica`, so one shard runs once in the whole application,
- `all` runs every shard on every replica, for sources that split the work themselves.

The number of replicas and the number of this replica come from [Running several replicas](replicas.mdx). A replica of a processor with fewer shards than replicas may run none of its shards.

## Configuration

The number of shards is `shards` of the processor, or `defaultShards` of its class. The other keys can also be set for every processor under `defaults`:

<CodeBlock language="yaml" title="application.yaml">{ProcessingYaml}</CodeBlock>

- `shards` must not be more than `slots`,
- `enabled: false` leaves the processor stopped until it is started through the manager, and `autostart: false` leaves every processor idle,
- `on-completion` is `stop`, the default, so a shard whose work ends becomes `Completed`, or `restart`, which starts it again after `completion-delay`,
- `shutdown-timeout` is how long stopping a processor, and closing the application, waits for its shards.

A key under `coilix.processors` that matches no processor is logged as a warning at startup.

## Restarts

When the work of a shard fails, only that shard waits for the backoff of `restart` and starts again, with `prepare`. When it fails more than `max-attempts` times within `within`, it becomes `Failed` and stays so until it is started through the manager. A shard that ran for `reset-after` without failing, 5 minutes by default, starts counting again, so rare failures do not use up the attempts.

## Control the processors

Beans control processors through the `ProcessorManager`: `start`, `stop`, `restart` of a processor or of one shard, `status` with the state of each shard and its last failure, and `topology` with the shards of this replica:

<CodeBlock language="scala" title="Maintenance.scala">{Maintenance}</CodeBlock>

The operations run one at a time on the thread `coilix-processor-manager` and change only this replica. Starting a running processor or stopping a stopped one changes nothing. Restarting a shard that another replica runs throws `ShardNotOwnedException` with the replica that runs it.

## Statistics and events

`statistics(id)` of the manager returns, for each shard of this replica, its state with the counters of its worker: processed and failed elements, the total and longest processing time, the time of the last element and the elements waiting in each slot. The counters survive restarts. A `BlockingProcessor` or a `CustomProcessor` records its own work through `shard.metrics`.

Every change of the state of a shard is published as `ProcessorEvent.ShardStateChanged`, and every failure of a worker as `ProcessorEvent.ShardFailed`. They are published on the thread of the manager, so a slow listener should be asynchronous:

<CodeBlock language="scala" title="FailureAlerts.scala">{FailureAlerts}</CodeBlock>

## Closing

When the application closes, the manager stops every shard at once, before any bean is destroyed, and logs the shards that did not stop within `shutdown-timeout`. Then it calls the `@PreDestroy` methods of the processors.
