This page shows how Coilix tells apart beans of the same generic trait, for example a repository for one effect type and a repository for another. Use it when two beans implement one trait with different type arguments and each dependency needs a particular one.

## Inject them by their full type

A constructor parameter of type `PriceSource[Option]` receives only the bean that extends `PriceSource[Option]`, so no `@Primary` or `@Qualifier` is needed:

<CodeBlock language="scala" title="PriceReport.scala">{PriceReport}</CodeBlock>

The same holds for `Option[PriceSource[List]]` and `List[PriceSource[Option]]`. A wildcard, as in `List[PriceSource[?]]`, matches every type argument. `ApplicationContext.getBean[PriceSource[Option]]` and the testkit's `bean[PriceSource[Option]]` look beans up by the full type too.

## Limits

Coilix reads the type arguments from the generic signatures that the compiler writes, so some types cannot be matched and stop the startup with an error that names the parameter:

- A type variable that nothing binds, as in `final class SqlPrices[F[_]](source: PriceSource[F])`. Create such a class in a `@Bean` method with a concrete type, for example `def prices: PriceSource[Option] = SqlPrices[Option]()`.
- A type lambda or a partially applied type, such as `PriceSource[[A] =>> Either[String, A]]`, because the JVM keeps only `Either` of it. Declare a named class for the effect instead.

A ready instance registered with only its class, without type arguments, does not match a dependency with type arguments. Register it with its full type, as `RegisteredBean.of[PriceSource[Option]](...)` does.
