This page shows how an application of Coilix uses Pekko actors and streams. Coilix creates one `ActorSystem` for the application, runs it on its own thread pools and stops it when the application closes.

## Add the module

Add `coilix-pekko` to the dependencies:

```scala
libraryDependencies += "dev.coilix" %% "coilix-pekko" % "<version>"
```

The module adds four beans:

- `actorSystem`, the `ActorSystem` of the application,
- `materializer`, the `Materializer` of Pekko Streams,
- `coilixActorSystem`, which creates the `ActorSystem` and stops it when the application closes,
- `pekkoSettings`, the settings under `coilix.pekko`.

## Run a stream

A bean receives the `Materializer` or the `ActorSystem` like any other dependency. A `using` parameter makes it available to the methods of Pekko that need it:

<CodeBlock language="scala" title="OrderTotals.scala">{OrderTotals}</CodeBlock>

An application bean of type `ActorSystem` or `Materializer` takes the place of the one from the module.

## Thread pools

Pekko starts no thread pools of its own:

- the default dispatcher runs on the `TaskExecutor` from [Background tasks and scheduling](tasks-and-scheduling.mdx). That is the compute pool of [cats-effect](cats-effect.mdx), so actors, streams and `IO` share one compute pool,
- `pekko.actor.internal-dispatcher`, which Pekko uses for its own work, is the default dispatcher,
- `pekko.actor.default-blocking-io-dispatcher`, which blocking stages such as file sources and sinks use, runs on the `BlockingExecutor`, by default on virtual threads:

<CodeBlock language="scala" title="ReportFiles.scala">{ReportFiles}</CodeBlock>

A dispatcher of your own runs on the `BlockingExecutor` too with `executor = "dev.coilix.pekko.BlockingExecutorConfigurator"`.

## Configuration

The settings of the module and the configuration of Pekko are in the configuration of the application, under `coilix.pekko`. Pekko does not read a separate `application.conf`:

<CodeBlock language="yaml" title="application.yaml">{PekkoYaml}</CodeBlock>

- `system-name` is the name of the `ActorSystem`, `coilix` by default,
- `shutdown-timeout` is how long the application waits for the `ActorSystem` to stop, 30 seconds by default,
- `config` holds the configuration of Pekko, with keys that start with `pekko`, over the defaults of Coilix and Pekko. Pekko logs through SLF4J.

## Closing

When the application closes, Coilix stops the `ActorSystem` with a coordinated shutdown, after every bean that uses it and before the thread pools it runs on. Pekko registers no shutdown hook of its own and never ends the JVM itself, whatever the configuration says, so it does not race with the closing of the application.

If the `ActorSystem` stops while the application runs, as Pekko does after a fatal error in an actor or a stream, Coilix reports it to its `FatalErrorHandler` as `ActorSystemStoppedException`, so the application closes and ends as described in [Fatal errors](fatal-errors.mdx).
