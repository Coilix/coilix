This page shows how a bean runs work in the background or on a schedule without creating its own threads. Coilix owns the threads, so it stops them when the application stops. Use these beans whenever a bean would otherwise call `Executors.newFixedThreadPool` or start a `Thread`.

## Two executors: computation and waiting

Every application has two executors, because work that computes and work that waits need different threads:

- `TaskExecutor` is the compute pool: a fork-join pool with one platform thread per processor, named `coilix-compute-<number>`. Computation, `@Async` methods and asynchronous event listeners run here. A task handed over from one of its threads usually stays on the same thread, which keeps the processor cache warm.
- `BlockingExecutor` is for calls that wait, such as JDBC queries, HTTP requests and file access. Each task gets a new virtual thread named `coilix-blocking-<number>`, which costs almost nothing while it waits. On JDK 17, which has no virtual threads, it uses a pool of up to 64 platform threads.

With the [cats-effect](cats-effect.mdx) module, the compute pool of cats-effect takes the place of the fork-join pool, and the threads are named `io-compute-<number>`.

Keep them apart. A blocking call on the compute pool holds one of its few threads, and with it a processor core, while it waits. Computation on the blocking executor does not help either: virtual threads share carrier threads, one per core, and a task that computes holds its carrier.

## Run a method asynchronously with @Async

Annotate a method with `@Async` to run it on the compute pool whenever another bean calls it, or with `@Async(blocking = true)` to run it on the blocking executor. Sending a mail waits for the mail server, so the mailer below blocks. The method must be declared in a trait of the bean:

<CodeBlock language="scala" title="InvoiceMailer.scala">{InvoiceMailer}</CodeBlock>

<CodeBlock language="scala" title="SmtpInvoiceMailer.scala">{SmtpInvoiceMailer}</CodeBlock>

A method returning `Future[T]` returns the result of the run on the executor, and a method returning `Unit` is started without waiting; its failure is logged. Methods without `@Async` run on the calling thread.

Coilix registers such a bean as a proxy of the trait, so other beans inject `InvoiceMailer`, not `SmtpInvoiceMailer`. A call from inside the bean itself does not pass the proxy and runs on the calling thread. An `@Async` method that no trait declares, or that returns something other than `Unit` or `Future`, stops the startup with `InvalidAsyncMethodException`.

## Keep the logging context in tasks

A task runs on another thread, but its log lines keep the MDC of the thread that handed it over, such as a request id put there by an HTTP filter. Coilix copies the MDC when a task is submitted, through `execute`, `submit`, `executionContext`, an `@Async` method or an asynchronous event listener, or when it is scheduled, and gives the thread its own MDC back when the task ends, so nothing leaks to the next task of a pooled thread. Set `coilix.concurrency.propagate-mdc: false` to turn it off.

The MDC needs a logging backend that keeps it, such as Logback or Log4j 2. `slf4j-simple` ignores the MDC. With Log4j 2, set `shutdownHook="disable"` on its `Configuration`: otherwise Log4j stops logging in its own shutdown hook while Coilix is still closing the application, and the last lines are lost.

## Repeat a method with @Scheduled

Annotate a method of a bean with `@Scheduled` to run it repeatedly. Set `fixedRate` for the time between the starts of two runs, or `fixedDelay` for the pause between the end of one run and the start of the next, and optionally `initialDelay`:

<CodeBlock language="scala" title="PriceRefresher.scala">{PriceRefresher}</CodeBlock>

Durations are written like configuration values, such as `10s` or `5 minutes`, or as a placeholder with a default, as in the example. The method takes no parameters and may be private.

The runs start when every bean of the application exists, and stop when the application starts stopping, before any bean is destroyed. A method that takes parameters, sets both `fixedRate` and `fixedDelay`, sets neither, or has a duration that cannot be read stops the startup with `InvalidScheduledMethodException`, which names the bean and the method.

## Repeat a task from code

When the schedule is known only at runtime, use the `TaskScheduler` bean. It runs a task once after a delay (`schedule`), at a fixed rate (`scheduleAtFixedRate`), or with a fixed pause between runs (`scheduleWithFixedDelay`). Each method returns a `ScheduledTask` with `cancel()`.

<CodeBlock language="scala" title="StockRefresher.scala">{StockRefresher}</CodeBlock>

Scheduled tasks run on a separate pool, `coilix-scheduler-<number>`, with one thread by default. If one run throws an exception, Coilix logs it and the task still runs next time. Runs of the same task never overlap.

## Retry failed work

`RetryPolicy` says how many times to try failed work and how long to wait between the tries. The wait starts at `initialDelay`, grows by `multiplier` after each failed try and never exceeds `maxDelay`. `jitter` spreads each wait randomly, here by up to 20% in both directions, so replicas that failed together do not retry at the same moment. `delayAfter(attempts)` returns the wait after that many failed tries, or `None` when no tries are left:

<CodeBlock language="scala" title="tasks/RetryingMailer.scala">{RetryingMailer}</CodeBlock>

The policy keeps no state, so one instance can serve every call. `RetryPolicy.default` makes five tries with waits from 1 second to 1 minute, `RetryPolicy.fixed(3, 2.seconds)` waits the same time between three tries, and `RetryPolicy.none` does not retry.

## Configure the threads

All keys under `coilix.concurrency` are optional. This configuration gives the compute pool four threads, lets at most 20 blocking calls run at once, for example to match a connection pool of 20, and gives the scheduler two threads:

<CodeBlock language="yaml" title="application.yaml">{TasksYaml}</CodeBlock>

Without configuration, the compute pool has `compute.threads` equal to the number of processors available to the JVM, which in a container is its CPU limit. The blocking executor has no limit, uses virtual threads, and with `blocking.virtual-threads: false` uses up to `blocking.platform-threads` platform threads (64 by default). Both wait 30 seconds for running tasks when the application stops. The scheduler has one thread named `coilix-scheduler-<number>` and waits 10 seconds by default. A scheduled method runs on that thread, so a method that computes or waits for long hands the work over to one of the executors.

Keep about one compute thread per processor. More threads that compute at the same time than processors only make the system switch between them.

## What happens when the application stops

`@Scheduled` methods stop first, in the `Producers` phase of closing described in [Bean lifecycle](bean-lifecycle.mdx#react-to-the-whole-context). The executor and the scheduler are closed like other beans when the application context closes, after the beans that use them. The scheduler drops the tasks that are still waiting for their time. Each of them then waits up to its `shutdown-timeout` for running tasks, interrupts those still running, and logs a warning with the number of tasks that did not finish.

## Use your own executor

To run tasks your own way, declare a `TaskExecutor` or `BlockingExecutor` bean. The default of that type is then left out and its threads are never created, so beans that require the executor receive yours.
