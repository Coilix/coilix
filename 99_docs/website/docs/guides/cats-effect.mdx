This page shows how an application of Coilix runs cats-effect `IO`. Coilix creates the `IORuntime`, closes it with the application, and makes its compute pool the only compute pool of the application, so `IO` fibers and the tasks of Coilix do not compete for the processor in two pools.

## Beans of the runtime

cats-effect is part of the core of Coilix, so `coilix-boot` brings it and there is nothing to add. The core adds five beans:

- `ioRuntime`, the `IORuntime` of the application, with the work-stealing pool of cats-effect: `coilix.concurrency.compute.threads` threads named `io-compute-<number>`, by default one per processor,
- `ioTaskExecutor`, the `TaskExecutor` from [Background tasks and scheduling](tasks-and-scheduling.mdx) on that pool. `@Async` methods and asynchronous event listeners run on `io-compute` threads,
- `coilixIORuntime`, which owns the runtime and shuts it down when the application closes, after the beans that use it. An application started as [`CoilixIOApp`](#start-as-an-ioapp) has no such bean, because its runtime belongs to the `IOApp`,
- `catsEffectSettings`, the settings under `coilix.cats-effect`,
- `ioRunnerAdapter`, which runs the `IOApplicationRunner` beans described in [Runners in IO](#runners-in-io).

The `BlockingExecutor` stays as it is, for blocking code outside `IO`.

## Start as an IOApp

An application written with `IO` starts as a `CoilixIOApp`, an `IOApp` of cats-effect:

<CodeBlock language="scala" title="CatsEffectApplication.scala">{CatsEffectApplication}</CodeBlock>

The application then lives in the main fiber of the `IOApp`:

- the runtime of the `IOApp` is the `ioRuntime` bean, with `coilix.concurrency.compute.threads` compute threads, so it stays the only compute pool. The number of threads is read before the command-line arguments, so set it in a configuration file, a system property or an environment variable,
- Coilix builds the context, runs the runners as described in [Runners in IO](#runners-in-io) and waits until the application is cancelled, for example by `SIGTERM` or Ctrl+C. Cancelling closes the context, so resources close in the reverse order of opening,
- with `coilix.cats-effect.exit-after-runners: true` the application closes and ends after its runners, which suits batch jobs,
- if the start or a runner fails, the context closes and the application ends with exit code 1.

`Coilix.run` from a plain `main` method works too: the module then creates the runtime itself and Coilix closes it with the application.

## Components in tagless final style

Services and repositories can be written for any effect `F[_]`, with the type classes of cats-effect as context bounds. `IO` is the effect of the application: the container binds the type parameter of such a component to `IO` and gives its context bounds the `ioAsync` bean, the `Async[IO]` instance, which also serves `Sync[IO]`, `Temporal[IO]` and `Concurrent[IO]`. ## Beans made by IO and Resource

A `@Bean` method may return `IO[A]` or `Resource[IO, A]`. The bean then has the type `A`: other beans receive the value of the effect or the opened resource, never the `IO` or the `Resource` itself.

<CodeBlock language="scala" title="DatabaseConfiguration.scala">{DatabaseConfiguration}</CodeBlock>

When the application starts, Coilix runs these effects on the `ioRuntime` bean:

- each bean waits for the beans it needs, so `migrations` runs after the pool is open,
- beans that do not depend on each other open at the same time, in parallel fibers,
- a resource closes when the application closes, after every bean that uses it, in the reverse order of opening,
- if an effect fails, the resources opened before it close and the startup stops with that failure.

A plain bean that depends on such a value is created as usual, after it. Use [`@DependsOn`](bean-lifecycle.mdx#order-beans-without-injecting-them) when a bean needs another one only through a side effect, for example a cache that reads tables the migrations create.

A bean made by an effect is always created at startup, so it cannot be `@Lazy` or `@Prototype`: such a bean stops the startup with `InvalidEffectfulBeanException`. Without the module, `Coilix.run` rejects these beans with `EffectfulBeanException`.

### Closing

Coilix waits for the finalizer of each resource at most `coilix.cats-effect.shutdown-timeout`, 30 seconds by default:

<CodeBlock language="yaml" title="application.yaml">{CatsEffectYaml}</CodeBlock>

`@ShutdownTimeout` on a `@Bean` method sets the limit of one bean, as a duration such as `"2m"` or a placeholder with a default, as in the example above. A finalizer that takes longer is cancelled and logged. A finalizer that fails is logged. In both cases Coilix goes on closing the other beans.

## Lifecycle methods in IO

`@PostConstruct` and `@PreDestroy` methods may return `IO[Unit]` instead of `Unit`:

<CodeBlock language="scala" title="ProductCache.scala">{ProductCache}</CodeBlock>

Coilix runs these effects on the `ioRuntime` bean:

- the `IO` of a `@PostConstruct` method runs after the methods that return `Unit` and before any other bean receives the bean. If it fails, the startup stops with a `BeanCreationException`,
- the `IO` of a `@PreDestroy` method runs when the application closes, before the methods that return `Unit`, within the same limit as the finalizer of a resource. If it fails, the failure is logged and closing goes on.

Such a bean, like a bean made by an effect, is always created at startup, so it cannot be `@Lazy` or `@Prototype`. Declare the methods on the class of the bean or, for a `@Bean` method, on the type it returns: Coilix finds them before it creates the bean. Without the module, `Coilix.run` rejects these beans with `EffectfulBeanException`.

## Runners in IO

A bean that extends `IOApplicationRunner` returns the startup logic as `IO[Unit]`:

<CodeBlock language="scala" title="PriceCheck.scala">{PriceCheck}</CodeBlock>

`IOApplicationRunner` and `ApplicationRunner` beans run in one list, ordered by `@Order` (runners without it run last), each after the previous one finishes. A failing `IO` stops the startup like an exception thrown by an `ApplicationRunner`.

## Blocking calls in IO

`IO.blocking` works as in any cats-effect application: the fiber blocks in place on a helper thread of cats-effect, and the compute pool gets a replacement thread in the meantime. It suits a few blocking calls at a time.

For many calls that wait at once, such as requests to a slow service, `IO.onBlockingExecutor` from `import dev.coilix.concurrency.CoilixIO.*` runs the call on a virtual thread of the `BlockingExecutor` instead, which costs almost nothing while it waits. The fiber continues on the compute pool afterwards.

## Fatal errors

After a fatal error in a fiber, such as an `OutOfMemoryError`, cats-effect prints the error and shuts down every runtime of the JVM. Coilix reports that shutdown to its `FatalErrorHandler` as `IORuntimeStoppedException`, so the application closes and ends as described in [Fatal errors](fatal-errors.mdx). A fatal error in a task of the `TaskExecutor` goes to the handler directly.

If your tests trigger a fatal error in a fiber, run them in their own test suite with parallel execution turned off, because the other runtimes of the JVM stop with it.

### Tests in IO

For test bodies that return `IO`, add munit-cats-effect to the test dependencies next to `coilix-testkit`:

```scala
libraryDependencies += "org.typelevel" %% "munit-cats-effect" % "<version>" % Test
```

A `CatsEffectSuite` with `CoilixIOSuite` registers tests with `coilixTest`. Each test gets a fresh context, given to its body like in `setup.use`, and the context closes when the `IO` of the test ends, also when it fails:

<CodeBlock language="scala" title="PriceCheckTest.scala">{PriceCheckTest}</CodeBlock>

The runtime of the suite is the `ioRuntime` bean of the context, so the test and the beans run on the same compute pool. Outside such a suite, `setup.useIO { ... }` and `setup.resource` from `import dev.coilix.testkit.CoilixIOTestSetup.*` use a setup in `IO`, and `setup.withIORuntime(runtime)` gives the context a runtime of your choice.
